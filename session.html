Qu'est-ce qu'une session utilisateur ?

Une session permet de maintenir l'état de connexion d'un utilisateur entre différentes requêtes HTTP. Les sessions mal configurées sont une source majeure de vulnérabilités.

🎯 Risques d'une gestion de session faible :

  • Session Hijacking : Vol de session via interception de cookies
  • Session Fixation : Forcer un utilisateur à utiliser un ID de session connu
  • Sessions non expirées : Sessions qui restent actives indéfiniment
  • Prédiction d'ID de session : ID de session facilement devinables
  • CSRF (Cross-Site Request Forgery) : Exploitation de sessions actives

💡 Mécanisme de session typique :

1. Utilisateur se connecte 2. Serveur crée une session avec ID unique 3. ID de session stocké dans un cookie 4. Cookie envoyé à chaque requête 5. Serveur valide la session

🔓 Session Vulnérable

Problèmes : Session sans expiration, ID prévisible

⚠️ Problèmes de sécurité :

// ❌ Code vulnérable sessionId = Math.floor(Math.random() * 10000); // ID simple et prévisible ! cookie = "sessionId=" + sessionId; // Pas de flags HttpOnly, Secure, SameSite // Pas d'expiration de session ! // Session reste active indéfiniment
  • ⚠️ ID de session prévisible (1-10000)
  • ⚠️ Aucune expiration de session
  • ⚠️ Cookie non sécurisé (pas HttpOnly)
  • ⚠️ Pas de régénération d'ID après login
  • ⚠️ Pas de validation côté serveur

✅ Session Sécurisée

Protections : Expiration, ID cryptographique, tokens

✅ Sécurité implémentée :

// ✅ Code sécurisé sessionId = crypto.randomUUID(); // ID unique et imprévisible cookie = { name: 'sessionId', value: sessionId, httpOnly: true, // Pas accessible en JS secure: true, // HTTPS uniquement sameSite: 'strict', // Protection CSRF maxAge: 1800 // Expire en 30 min } // Régénération après login // Validation côté serveur // Expiration automatique
  • ✅ ID de session cryptographiquement sécurisé (UUID)
  • ✅ Expiration automatique (30 minutes)
  • ✅ Cookie HttpOnly (protection XSS)
  • ✅ Cookie Secure (HTTPS uniquement)
  • ✅ SameSite strict (protection CSRF)
  • ✅ Régénération d'ID après login

⚔️ Attaques courantes sur les sessions :

1. Session Hijacking (Vol de session)

L'attaquant vole l'ID de session via XSS, reniflage réseau (sniffing), ou malware.

Protection : Cookies HttpOnly, HTTPS, IP binding, détection d'anomalies.

2. Session Fixation

L'attaquant fixe un ID de session connu avant que la victime se connecte.

Protection : Régénérer l'ID de session après authentification réussie.

3. CSRF (Cross-Site Request Forgery)

Exploitation d'une session active pour effectuer des actions non autorisées.

Protection : Tokens CSRF, SameSite cookies, vérification du Referer.

4. Sessions non expirées

Les sessions restent actives indéfiniment, augmentant le risque d'exploitation.

Protection : Timeout d'inactivité, expiration absolue, déconnexion automatique.

🛡️ Bonnes pratiques pour la gestion de sessions :

Génération de sessions :

  • ID imprévisibles : Utiliser des générateurs cryptographiques (UUID, crypto.randomBytes)
  • Longueur suffisante : Minimum 128 bits d'entropie
  • Régénération : Nouveau ID après login et changements de privilèges

Stockage et transmission :

  • Cookies sécurisés : HttpOnly, Secure, SameSite=Strict
  • HTTPS obligatoire : Chiffrement de toutes les communications
  • Stockage côté serveur : Ne jamais stocker de données sensibles dans les cookies

Expiration et validation :

  • Timeout d'inactivité : 15-30 minutes sans activité
  • Expiration absolue : Maximum 24 heures (selon le contexte)
  • Validation : Vérifier l'IP, User-Agent (avec prudence)
  • Déconnexion explicite : Invalider complètement la session

Protection contre les attaques :

  • Tokens CSRF : Pour toutes les actions sensibles
  • Limitation de sessions : Maximum 1-3 sessions simultanées par utilisateur
  • Journalisation : Logger toutes les activités de session
  • Détection d'anomalies : Surveiller les changements suspects (IP, localisation)
