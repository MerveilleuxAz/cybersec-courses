Qu'est-ce qu'une attaque par inférence ?

L'attaque par inférence consiste à extraire des informations sensibles en analysant les différences subtiles dans les réponses du système, même lorsque l'accès direct aux données est bloqué. L'attaquant déduit des informations à partir de ce que le système révèle indirectement.

🎯 Principes de base :

  • Analyse des réponses : Messages d'erreur, temps de réponse, codes HTTP
  • Énumération : Tester systématiquement différentes valeurs
  • Corrélation : Combiner plusieurs fuites d'information
  • Side-channel : Exploiter des canaux auxiliaires (timing, comportement)

💡 Exemple simple :

# Connexion avec mauvais identifiants Username: inconnu@email.com → "Cet email n'existe pas" ❌ Fuite d'information ! Username: admin@entreprise.com → "Mot de passe incorrect" ✓ L'email existe ! # L'attaquant vient d'énumérer un compte valide # Prochaine étape : brute force du mot de passe

🔓 Système Vulnérable

Testez ces emails :

admin@example.com (existe) user@example.com (existe) test@example.com (n'existe pas)

⚠️ Fuites d'information :

// ❌ Messages d'erreur trop précis if (!userExists(email)) { return "Cet email n'existe pas"; } if (!passwordMatch(password)) { return "Mot de passe incorrect"; } // L'attaquant peut énumérer les comptes !
  • ❌ Messages d'erreur différenciés
  • ❌ Temps de réponse différent
  • ❌ Codes HTTP spécifiques
  • ❌ Permet énumération d'utilisateurs

✅ Système Sécurisé

Même erreur pour tous les cas :

✅ Protections implémentées :

// ✅ Message générique if (!authenticate(email, password)) { // Délai artificiel constant await sleep(randomBetween(200, 300)); return "Identifiants incorrects"; } // Impossible de différencier les cas // Temps de réponse constant
  • ✅ Message d'erreur générique identique
  • ✅ Temps de réponse constant (timing constant)
  • ✅ Même code HTTP pour tous les échecs
  • ✅ Rate limiting pour limiter énumération

⚔️ Types d'attaques par inférence :

1. Énumération d'utilisateurs

Découvrir quels comptes/emails existent dans le système.

# Récupération de mot de passe Email: inconnu@test.com → "Email non trouvé" Email: admin@site.com → "Email de récupération envoyé" ✓ L'attaquant sait que admin@site.com existe # Inscription Email: user@site.com → "Cet email est déjà utilisé" ✓ Énumération de la base d'utilisateurs

2. Timing Attacks (Attaques temporelles)

Exploitation des différences de temps de traitement.

# Comparaison de mot de passe caractère par caractère Password: a*** → 10ms (échec immédiat) Password: p*** → 50ms (1er caractère ok !) Password: pa** → 90ms (2 caractères ok !) Password: pas* → 130ms (3 caractères ok !) # L'attaquant reconstruit le mot de passe # en mesurant le temps de réponse

3. Error-based Inference

Extraction d'informations via messages d'erreur.

# Upload de fichier File: document.pdf → "Fichier uploadé avec succès" File: malware.exe → "Extension .exe non autorisée" ✓ L'attaquant connaît les extensions bloquées # Accès fichier GET /files/1 → 200 OK GET /files/2 → 404 Not Found GET /files/3 → 403 Forbidden (existe mais accès refusé !) ✓ Énumération des IDs de fichiers existants

4. Boolean-based Blind Inference

Déduction d'informations par questions Vrai/Faux.

# Exemple : Blind SQL Injection ' AND (SELECT LENGTH(password) FROM users WHERE id=1) > 5 -- → Comportement A (Vrai) ' AND (SELECT LENGTH(password) FROM users WHERE id=1) > 10 -- → Comportement B (Faux) ✓ Le mot de passe fait entre 6 et 10 caractères # L'attaquant extrait les données bit par bit

💼 Cas d'usage réels d'inférence :

1. Vérification d'existence de comptes

  • Formulaires d'inscription : "Email déjà utilisé"
  • Récupération de mot de passe : "Email non trouvé" vs "Email envoyé"
  • Réseaux sociaux : Suggestions d'amis révélant des connexions

2. Information Leakage via API

# API REST mal sécurisée GET /api/users/123 → 200 OK + données GET /api/users/124 → 404 Not Found GET /api/users/125 → 403 Forbidden ✓ L'utilisateur 125 existe mais l'accès est refusé

3. Session et Authentification

# Cookie de session prédictible SessionID: user_123_20260131 ✓ L'attaquant devine les IDs de session # Tokens JWT mal configurés eyJ0eXAiOiJKV1QiLCJhbGci... ✓ Payload décodable (base64) révèle rôle, email, etc.

4. Recherche et filtres

# Moteur de recherche interne Recherche: "salaire" → 45 résultats Recherche: "salaire 50000" → 12 résultats Recherche: "salaire Jean Dupont" → 1 résultat ✓ Inférence du salaire d'un employé spécifique

⏱️ Timing Attacks (Analyse approfondie) :

Exemple : Comparaison de strings non sécurisée

// ❌ Code vulnérable (early return) function comparePassword(input, correct) { if (input.length !== correct.length) return false; for (let i = 0; i < input.length; i++) { if (input[i] !==correct[i]) return false; // ❌ Sort dès le 1er caractère incorrect } return true; } // Temps de réponse révèle la position du caractère incorrect !

Solution : Comparaison à temps constant

// ✅ Code sécurisé (constant-time comparison) function secureCompare(input, correct) { if (input.length !== correct.length) return false; let diff = 0; for (let i = 0; i < input.length; i++) { diff |=input.charCodeAt(i) ^ correct.charCodeAt(i); } // Délai artificiel aléatoire await sleep(randomBetween(100, 200)); return diff===0; }

🛡️ Défenses contre les attaques par inférence :

1. Messages d'erreur génériques

  • ✅ Même message pour tous les échecs d'authentification
  • ✅ "Identifiants incorrects" au lieu de "Email inconnu"
  • ✅ Codes HTTP cohérents (toujours 401 pour auth failed)

2. Timing constant

  • ✅ Constant-time comparison pour mots de passe/tokens
  • ✅ Délais artificiels : sleep(random(100, 200))
  • ✅ Crypto timing-safe : crypto.timingSafeEqual() (Node.js)

3. Rate Limiting et CAPTCHA

  • ✅ Limitation du nombre de tentatives (5/minute)
  • ✅ Augmentation progressive du délai (exponential backoff)
  • ✅ CAPTCHA après N échecs
  • ✅ Blocage temporaire d'IP

4. Réponses uniformes

  • ✅ Toujours renvoyer 200 OK (avec message d'erreur dans body)
  • ✅ Même format JSON pour succès et échec
  • ✅ Padding de réponses (taille identique)

5. Obfuscation d'IDs

  • ✅ UUIDs au lieu d'IDs séquentiels (1, 2, 3...)
  • ✅ Hashage d'IDs publics
  • ✅ Tokens aléatoires pour ressources sensibles

6. Validation d'accès stricte

  • ✅ Même erreur pour "n'existe pas" et "accès refusé"
  • ✅ Vérifier les permissions AVANT de révéler l'existence
  • ✅ Filtrer les données sensibles des réponses API

✅ Checklist anti-inférence :

  • ☑️ Messages d'erreur génériques et identiques
  • ☑️ Comparaisons à temps constant (mots de passe, tokens)
  • ☑️ Rate limiting sur toutes les endpoints sensibles
  • ☑️ Délais de réponse constants ou aléatoires
  • ☑️ Codes HTTP cohérents (pas de 404 vs 403)
  • ☑️ UUIDs au lieu d'IDs séquentiels
  • ☑️ Journalisation des tentatives répétées
  • ☑️ CAPTCHA après plusieurs échecs
  • ☑️ Pas de révélation d'existence via recherche/API
  • ☑️ Audit régulier des fuites d'information potentielles
